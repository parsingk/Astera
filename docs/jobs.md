# Job은 어떻게 도는가

Job(Run) 하나가 만들어져서 지워질 때까지 무슨 일이 일어나는지 순서대로 적었습니다.
1~6절은 예약이 아닌 보통 Job이고, 7절이 예약 Job, 8절이 GitHub까지 진행하는 Job입니다.

## 먼저: 프로젝트가 git 저장소여야 합니다

**Job을 만들기 전에 프로젝트 폴더가 git 저장소로 초기화되어 있어야 합니다.**

Job의 워커는 언제나 git 워크트리에서 일합니다. 저장소가 아니면 워크트리를 만들 수 없으므로,
`실행`을 누른 Job은 시작하지 못하고 Gate에 이유가 뜹니다. 만드는 것 자체는 막지 않지만
돌지는 않습니다.

아직 저장소가 아니라면 프로젝트 폴더에서 다음을 먼저 하세요.

```
git init
git add -A
git commit -m "first commit"
```

그리고 **HEAD가 브랜치를 가리켜야 합니다.** bisect나 rebase 중이거나 특정 커밋을 직접
체크아웃한 상태(detached HEAD)면 갈라져 나갈 자리가 없어서 같은 이유로 멈춥니다.

## 1. 만들기

Job을 만들면 아무것도 시작하지 않습니다. Task를 추가해도 돌지 않습니다.
Task를 다 짠 뒤 상세 창의 `실행`을 눌러야 시작합니다.

코디네이터 계정이 있는 Job은 Task 없이 실행해도 됩니다. MCP `create_job`이나 `astera jobs create`로
만든 Job이 그렇습니다. 그때는 코디네이터가 목표를 먼저 몇 개의 Task로 나누고(의존 관계, 계정,
프로젝트의 실행 구성으로 검증까지 붙여서) 그 Task들을 돌립니다. Task가 있는 Job은 짜 둔 그대로
돌리고 Task를 새로 만들지 않습니다.

`runs stop`(MCP `stop_run`)은 열린 워커를 닫고 그 회차의 코디네이터도 멈추며 회차를 세웁니다.
이미 끝난 회차(모든 Task가 완료되었거나, 재시도가 남지 않은 채 실패한 회차)는 CONFLICT로 거절하고 그대로 둡니다.
끝난 회차는 멈출 필요가 없습니다. 그 회차의 코디네이터와 할 일이 끝난 워커는 저절로 끝납니다. 회차가 끝난
때와 사람이 그 세션에 마지막으로 입력한 때 중 늦은 쪽에서 10분 동안 아무도 입력하지 않으면 끝납니다.
그 사이에는 탭에서 코디네이터의 마무리 요약을 읽거나 이어서 물어볼 수 있고, 입력할 때마다 10분을 다시 셉니다.
입력으로 치는 것은 Astera 탭에서 친 것, 그리고 Host가 운전할 때의 Slack 답장뿐입니다. `sessions send`는
에이전트도 쓰므로 치지 않습니다. 답하는 중인(바쁜) 세션은 한 시간까지는 도중에 끝내지 않고,
한가해진 뒤에 끝냅니다. 10분이 지나고도 한 시간 넘게 바쁜 표시가 남아 있으면 멈춘 것으로 보고 끝냅니다.
예약 실행의 회차는 지켜보는 사람이 없으므로 끝나자마자 정리합니다. `worker-retain`으로 붙잡아 둔 워커는
끝내지 않습니다. 코디네이터를 곧바로 끝내려면 CLI에서 `astera run-coordinator-stop --run <runId>`를 씁니다.
`runs resume`(MCP `resume_run`)은 회차를 다시 돌리고, 코디네이터 계정이 있는 Job이면 새 코디네이터를
띄웁니다. 새 코디네이터는 이미 끝난 것을 먼저 살펴보고 이어서 합니다. 멈춘 코디네이터가 아직
종료되는 중이면 10초까지 기다리고, 그래도 남아 있으면 아무것도 바꾸지 않고 거절합니다. 잠시 뒤
다시 하면 됩니다.

코디네이터는 계획하고 배치만 합니다. 파일을 고치지 않습니다. 코디네이터 세션은 회차의 워크트리가
아니라 프로젝트 폴더 자체에서 돌기 때문에, 고치고 빌드하고 커밋하는 일은 전부 Task를 받은 워커가
합니다.

이 시점에는 디스크에 아무것도 만들지 않습니다. 실행하지 않은 Job이 빈 폴더를 남기지 않습니다.

## 2. `실행`

**그 Job만의 작업 폴더(git 워크트리)가 하나 생깁니다.**

워크트리는 **프로젝트 폴더의 현재 브랜치**에서 갈라집니다. `develop`에서 일하고 있으면
워크트리도 `develop`에서 갈라집니다. 프로젝트의 기본 브랜치가 아닙니다 — 그러면 나중에 합칠 때
관계없는 조상을 끌고 옵니다.

이때부터 **에이전트는 프로젝트 폴더를 건드리지 않습니다.** 사용자가 그 폴더에서 파일을 편집하고
있어도 서로를 밟지 않습니다.

## 3. Task가 도는 방식

동시 실행 값이 갈림길입니다. 새 작업 모달의 `동시 실행` 칸이고, **기본값은 3입니다**.

**동시 실행 2 이상 (기본값 3)** — Task마다 자기 워크트리가 생깁니다. 어떤 Task가 앞선 Task들에
의존하면 그것을 시작하기 전에 앞의 결과를 Job의 워크트리로 모읍니다.

- 앱이 스스로 합칩니다.
- 충돌하면 `워크트리 병합` Task를 만들어 에이전트에게 넘깁니다. 사람을 부르는 것은 마지막으로
  미룹니다.
- 합쳐진 Task 워크트리는 그 자리에서 정리됩니다. 폴더가 쌓이지 않습니다.

**동시 실행 1** — Task들이 한 워크트리를 순서대로 물려받습니다. 1번이 끝나면 2번이 같은
폴더에서 그 결과 위에 이어서 일합니다. 합칠 것이 생기지 않습니다.

그래프 노드의 `띄우기` 버튼은 Task 하나를 손으로 다시 띄웁니다(Gate에서 막힌 것을 재시도할 때).
**동시 실행 1인 Job에만 있습니다** — 2 이상이면 워커가 각자의 워크트리에서 도는데, 손으로 띄운
워커는 Job 워크트리로 가 통합 Task가 합칠 자리를 밟습니다. 그래서 버튼 자체를 없앴고, 그 자리를
스케줄러가 대신 맡습니다. 기본값이 3이므로 **기본값으로 만든 Job에는 이 버튼이 나오지 않습니다.**

`실행`을 누르기 전에도 없고, 예약 템플릿에도 없습니다 — 템플릿은 자기 Task를 돌리지 않고 회차가
돕니다(7절). 회차에서는 그대로 보입니다.

### sandbox 안의 워커와 검사

워커가 sandbox 안에서 일한 Task는 검사(`--validate`)도 같은 종류의 sandbox 안에서 돕니다. 검사는 워커가 고친
파일(패키지 스크립트, 테스트, 빌드 파일)을 실행하기 때문입니다. 워커가 sandbox 안에서 일하는 경우는 둘입니다.
에이전트 프로필의 `sandbox 에서 실행`이 켜져 있었거나, sandbox 안의 세션이 그 Job이나 Task를 만들었습니다. 뒤의
경우 워커는 어느 프로필을 쓰든 sandbox 안에서 시작합니다.

- Codex 워커의 검사는 그 세션과 같은 권한 프로필로 `codex sandbox` 안에서, 같은 계정으로 돕니다.
- Claude Code 워커의 검사는 macOS와 Linux에서 Claude Code의 sandbox가 쓰는 런타임 안에서 돕니다. 네트워크는
  세션처럼 열려 있습니다.
- sandbox를 씌울 수 없으면(계정의 Windows sandbox가 아직 설정되지 않았다, 런타임에 필요한 도구가 없다)
  검사를 sandbox 밖에서 돌리지 않습니다. 코드의 실패로 치지도 않고 사람에게 묻습니다: 다시 시도, 이 검사
  건너뛰기, 실패로 표시. 질문은 이유와 할 수 있는 일을 함께 말합니다. 예를 들어 계정의 Windows sandbox가
  설정되지 않았으면 설정 › 에이전트 프로필에서 sandbox 프로필 아래 그 계정의 설정하기를 누른 뒤 다시 시도하라고
  합니다. 검사가 시작되기 전에 sandbox가 멈춘 경우도 같은 질문이 되고, 코드의 실패로 치지 않습니다. 다만 macOS와
  Linux의 Codex 검사는 예전처럼 터미널에서 곧바로 돌므로, 거기서 sandbox가 멈추면 아직 검사의 실패로 읽힙니다.
  Docker 검사(`compose`, `dockerfile`)도 같은 질문이 됩니다. Docker는 sandbox 밖에 닿기 때문입니다.
- Windows의 Claude Code에는 자기 sandbox가 없습니다. 워커의 셸이 Codex sandbox 안에서 돌았으면(Codex 계정의
  Windows sandbox가 설정되어 있을 때) 검사도 Codex 워커의 검사처럼 `codex sandbox` 안에서, 그 셸이 빌린 Codex
  계정과 같은 권한 프로필로 돕니다. 검사를 시작할 때 그 길이 없어졌으면 검사를 돌리지 않고 위처럼 사람에게
  묻습니다. 워커가 모두 파일 도구만 막힌 채(deny 규칙만으로) 일했다면 검사는 예전처럼 sandbox 밖에서 돌고, 결과
  옆에 `sandbox 밖에서 검증함`이라고 적힙니다.
- 검사는 sandbox 여부와 상관없이 Credentials 목록이 그 폴더의 세션에 숨기는 변수 없이 시작합니다. 결과에는 빠진
  변수의 이름이 적히고(값은 적지 않습니다), 실패한 검사 아래에 보입니다. 두 번 시간을 넘긴 검사는 묻는 질문에 그
  이름을 적습니다. 검사에 꼭 필요한 값(사설 레지스트리의 토큰 같은 것)은 실행 구성의 `env`에 일부러 넣을 수
  있습니다. 그 값은 숨긴 뒤의 환경 위에 얹힙니다.
- 그런 Task의 검토자도 구현자의 워크트리에서 일하므로 자기 CLI의 sandbox 안에서 시작합니다. Windows의 Claude
  Code 검토자는 sandbox 프로필의 Claude Code 세션처럼 시작합니다. 셸이 Codex sandbox 안에서 돌 수 있으면(Codex
  계정의 Windows sandbox가 설정되어 있으면) sandbox 안에서 시작하고, 완료 블록에 따로 적히는 것은 없습니다. 그
  길이 없으면 무엇이 작업을 sandbox에 넣었는지에 따라 갈립니다.
  - 프로필의 `sandbox 에서 실행`으로 sandbox 안에서 한 작업: 검토자는 파일 도구만 로그인 폴더에서 막힌 채
    시작합니다(셸은 제한 없음). 완료 블록에 `파일 도구 보호만으로 검토했습니다`라고 적힙니다.
  - sandbox 안의 세션이 만든 Job이나 Task: 그런 작업의 다른 시작처럼 검토자도 시작하지 않습니다. 거절에는
    이유마다 다른 코드가 붙고(`SANDBOX_UNAVAILABLE: windows-setup codex <계정>`, `cli-missing codex`,
    `no-sandbox claude` 등), 검토는 사람에게 묻습니다.

### 외부 검토자

검토를 요청한 Task(`--review`)는 보통 구현한 쪽의 반대편 모델이 검토합니다. 설정에서 **외부 검토자**를 고르면 그 검토를 다른 에이전트(Gemini CLI, Copilot CLI, OpenCode, 또는 ACP를 쓰는 아무 에이전트)가 대신합니다. 외부 검토자는 검토만 합니다. 워커나 코디네이터가 되지 않고, 계정도 터미널 탭도 없습니다. 고르는 값은 앱 전체에 하나이고, Job이나 Task마다 따로 고를 수 없습니다. 고르지 않으면(`자동 (상대 쪽 모델)`) 지금까지와 똑같이 움직입니다.

**설정하기.** 설정 › 에이전트 탭의 `검토자` 묶음에서 합니다. `검토자 추가`로 Gemini CLI, Copilot CLI, OpenCode 중 하나를 고르거나 `직접 입력`으로 이름과 명령을 적고, 위쪽 선택칸에서 그 검토자를 고릅니다. 에이전트는 먼저 그 컴퓨터에 설치되고 로그인되어 있어야 합니다. Astera가 대신 로그인해 주지 않습니다. `테스트`를 누르면 에이전트를 잠깐 띄워 보고 여섯 가지 중 하나로 답합니다.

- `연결됐습니다`: 에이전트의 이름과 버전이 보입니다.
- `명령을 찾지 못했습니다`: 설치되지 않았거나 명령이 틀렸습니다.
- `에이전트에 로그인이 필요합니다`: 그 에이전트를 터미널에서 한 번 실행해 로그인하세요.
- `에이전트가 제때 응답하지 않았습니다`: `npx`로 처음 받아 실행하면 몇 분 걸릴 수 있으니 한 번 더 눌러 보세요.
- `에이전트의 ACP 버전을 Astera 가 지원하지 않습니다`: 에이전트를 업데이트하거나 다른 에이전트를 쓰세요.
- `테스트에 실패했습니다`: 에이전트가 시작은 했지만 중간에 멈췄거나 Astera가 쓸 수 없는 방식으로 답했습니다. 뒤따르는 메시지를 읽고, 그 에이전트를 터미널에서 직접 실행해 보세요.

**읽기만 한다는 말이 지켜 주는 것과 지켜 주지 못하는 것.**

- 에이전트에게는 읽기만 하고 테스트나 빌드는 돌리지 말라고 이릅니다. 에이전트가 읽기 말고 다른 권한을 물으면 모두 거절하므로, 묻고 나서 돌리는 명령은 돌지 않습니다.
- 반면 에이전트가 자기 규칙으로 묻지 않고 돌리는 명령(에이전트에 따라 `git status`나 `git diff`)은 Astera가 막지 못합니다.
- 에이전트가 묻지 않고 파일을 바꾸면 그 검토를 바로 멈춥니다.
- 검토하는 동안 그 폴더의 추적되는 파일이 바뀌었고 그 폴더에서 일한 다른 작업이 없었다면, 그 판정은 쓰지 않습니다. 이미 바뀌어 있던 파일을 한 번 더 고친 것도 알아챕니다. 검토 전에는 읽히던 폴더 상태를 검토 뒤에 읽지 못해도 바뀐 것으로 봅니다.
- 에이전트가 새로 만든 추적되지 않는 파일은 알아채지 못합니다.
- 외부 검토자는 sandbox 안에서 돌지 않습니다. 그래서 작업이 sandbox 안에서 돈 Task는 외부 검토자에게 넘기지 않고 멈춥니다. 그런 Task는 `자동`으로 검토하세요.
- 외부 검토자는 검사와 마찬가지로 Credentials 목록이 그 폴더의 세션에 숨기는 변수 없이 시작합니다. 그래서 로그인에 쓰는 키를 그 목록이 숨기고 있으면 에이전트가 로그인하지 못하고, 검토는 로그인이 필요하다는 이유로 멈춥니다.

**무엇을 읽나.** 자동 검토와 같은 검토 지시문, 바뀐 파일 목록, 검사 결과를 읽습니다. 그 작업의 첫 시도가 시작한 커밋을 Astera가 기록해 두었으면 거기서 지금의 HEAD까지의 diff도 함께 받고(150KB까지), 기록이 없거나 바뀐 것이 없으면 목록의 파일을 직접 읽습니다.

**판정 뒤.** 판정은 자동 검토와 같은 길로 들어갑니다. 통과하면 Task가 완료되고, 문제를 찾으면 자동 수정이 켜진 Run에서는 같은 횟수 한도 안에서 수리로 돌아갑니다.

**멈추는 경우.** 외부 검토자가 검토를 끝내지 못하면 `상대 쪽 모델`로 몰래 바꿔 검토하지 않습니다. Task가 `blocked`가 되고 `검토를 실행할 수 없습니다: ...`로 시작하는 질문이 열려 사람을 기다립니다. 이유는 영어로 적히고, 시작 부분은 아래와 같습니다(`{이름}`은 그 검토자의 이름). 검토를 시작한 뒤에 멈추면 이유 끝에 `Transcript:`와 에이전트가 한 말의 기록 파일 경로가 붙습니다. 질문에 답하면 Task가 다시 진행되는데 이미 끝난 일이 다시 구현될 수 있으니, 결과가 괜찮으면 `task-update --status completed`로 닫으세요.

| 이유의 시작 | 뜻과 할 일 |
| --- | --- |
| `the external reviewer {이름} could not be started: ... was not found` | 명령을 찾지 못했습니다. 설치하거나 설정의 명령을 고치세요. |
| `the external reviewer {이름} needs a sign-in` | 로그인이 필요합니다. 그 에이전트의 CLI로 터미널에서 먼저 로그인하세요. 로그인에 쓰는 키를 Credentials 목록이 그 폴더에서 숨기고 있어도 이렇게 멈춥니다. |
| `the external reviewer {이름} did not finish in 20 minutes` | 20분 안에 끝내지 못했습니다. 변경이 너무 크거나 에이전트가 멈췄으니 에이전트를 확인하세요. |
| `the external reviewer {이름} stopped before giving a verdict` | 판정 전에 에이전트가 종료됐습니다. 뒤따르는 종료 코드와 오류 끝부분을 보고 에이전트를 고치세요. |
| `the external reviewer {이름} changed a file without asking` | 에이전트가 묻지 않고 파일을 바꿨습니다. 판정은 쓰지 않습니다. 폴더를 확인하고, 에이전트가 편집 전에 묻도록 설정하세요. |
| `files in ... changed while the external reviewer {이름} ran` | 검토 중 폴더의 파일이 바뀌었습니다. 판정은 쓰지 않습니다. 그 폴더를 건드리지 않은 채 Task를 다시 진행시키세요. |
| `the external reviewer {이름} ended without a readable verdict` 또는 `ended its turn with ...` | 읽을 수 있는 판정이 없었습니다(형식이 틀리면 한 번 더 묻고, 그래도 안 되면 멈춥니다). 에이전트를 확인하거나 다른 에이전트를 쓰세요. |
| `the external reviewer {이름} could not be used` 또는 `could not be started` | 시작하거나 프로토콜을 맞추지 못했습니다(지원하지 않는 버전 등). 뒤따르는 이유를 보고 테스트 버튼으로 확인하세요. |
| `this task's work ran in a sandbox, and the external reviewer {이름} cannot be sandboxed` | sandbox 안에서 한 작업입니다. 설정의 검토자를 `자동`으로 바꾸거나 손으로 완료하세요. |
| `no implementation dispatch for task ...` | 검토할 구현 기록이 없습니다. 그 Task의 구현이 실제로 돌았는지 확인하세요. |
| `the Run of task ... has no folder of its own to review in` | 그 Run에 검토할 자기 폴더가 없습니다. Run의 폴더(워크트리)가 남아 있는지 확인하세요. |
| `Error:` 뒤에 `허용되지 않은 경로입니다` (앱 언어로 적힘) | 검토할 폴더가 Astera가 일해도 되는 곳이 아닙니다. 그 폴더가 Job이나 워크트리의 것인지 확인하세요. |
| `could not read the reviewer setting` | 앱 설정 파일을 읽지 못했습니다. 파일을 확인하세요. |
| `the verdict of the external reviewer {이름} was refused` | 판정은 나왔지만 Astera가 받아 주지 않았습니다. 뒤따르는 이유를 보세요. |

표에 없는 이유는 적힌 그대로 읽으면 되고, 그 Task도 같은 방식으로 사람을 기다립니다.

**Astera가 꺼져 있어도** Host가 같은 설정을 읽어 외부 검토를 직접 돌립니다. 보통처럼 Host가 Job을 돌리고 있으면 앱을 꺼도 돌고 있는 외부 검토는 그대로 이어집니다. 검토를 돌리던 프로세스가 사라지면 그 검토는 사라집니다. Host가 다시 시작되거나 바뀔 때, 또는 앱이 직접 Job을 돌리던 중에 앱을 끌 때가 그렇습니다. 그 Task는 자동 수정이 켜진 Run이면 다시 검토되고, 아니면 사람에게 묻습니다.

**어디서 보나.** Run 상세의 검토 표시와 결과 보고의 검토 줄에 검토자의 이름이 나옵니다. 에이전트가 한 말의 기록은 프로필 안, 검토 지시문 폴더 옆의 `review-logs` 폴더에 `<Task id>-<Dispatch id>.log`라는 텍스트 파일로 남습니다. 검토가 끝나도 지워지지 않고 14일 동안 보관되며, 200개가 넘으면 오래된 것부터 지워집니다. 그 검토를 `worker-read`로 읽으면 터미널 출력 대신 이 폴더를 알려 줍니다.

## 4. 끝난 뒤 — 병합은 사람이 누릅니다

**작업이 끝나도 자동으로 합쳐지지 않습니다.** 상세 창의 `병합` 버튼을 눌러야 합니다.

병합은 사용자가 체크아웃해 둔 브랜치의 작업 트리를 바꿉니다. 사용자가 그 폴더에서 일하는 중일
수도 있고, 충돌하면 그 트리가 반쯤 병합된 상태로 남습니다. 그 순간은 사람이 고릅니다.

`병합`을 누르면 프로젝트 폴더에서 워크트리의 브랜치를 합칩니다.

| 상황 | 결과 |
|---|---|
| 프로젝트 브랜치가 그대로였음 | fast-forward — 새 커밋 없이 워크트리의 커밋이 그대로 프로젝트 브랜치의 히스토리가 됩니다 |
| 그 사이 프로젝트 브랜치가 움직였음 | 병합 커밋 하나가 생깁니다 |
| 프로젝트 폴더에 커밋되지 않은 변경이 있음 | 합치지 않고 이유를 보여줍니다. 아무것도 잃지 않습니다 |
| 충돌 | 합치기 전 상태로 되돌리고 이유를 보여줍니다 |
| 워크트리 폴더가 이미 없음 | 합칠 것이 남아 있지 않다고 알려 줍니다 |

`병합`은 푸시하지 않습니다(GitHub까지 진행하는 Job은 Run의 브랜치를 푸시합니다 — 8절). 브랜치를 바꾸지도
않습니다. 프로젝트 폴더의 현재 브랜치가 병합 대상입니다.

병합한 뒤에도 워크트리 폴더는 남습니다. 결과를 보고 다시 합칠 수 있고, 폴더 정리는 삭제할 때
고릅니다.

### How It Works 기록

설정에서 How It Works 추적을 켜 두었다면, 끝난 Run 하나가 기록 하나가 됩니다. 이 기록은 Astera
Host가 씁니다. 그래서 Astera 창을 닫아 둔 사이에 끝난 Run도 기록되고, 앱을 다시 열면 How It
Works에 보입니다. MCP의 `regenerate_work_record`로 설명을 다시 쓰게 할 때도 앱이 열려 있지 않아도
됩니다.

사람이 직접 연 세션의 작업도 Host가 기록합니다. Host가 돌리는 세션이면 앱을 닫아 둔 사이에 끝난
작업도 기록되고, 그 세션의 `session-task-start`와 `session-task-complete`도 앱 없이 답을 받습니다.
다만 세션을 기록할지는 여전히 How It Works 추적 설정이 정합니다. 추적이 꺼져 있으면 앱이 열려 있든
아니든 세션의 작업은 기록되지 않습니다.

Host가 How It Works를 쓰기 전 버전의 Astera 앱이 Host에 붙어 있는 동안에는 그 앱이 기록을 쓰고
Host는 쓰지 않습니다. 그동안 `regenerate_work_record`는 `CONFLICT`로 거절되니, 앱을 업데이트하거나
앱에서 다시 쓰세요.

### 결과 보고

Run이 끝나면 Host가 요약 하나를 만들어 Run에 저장합니다. Run 상세 맨 위의 카드가 그것이고, `복사`로
Markdown을 가져갈 수 있습니다. 카드에는 완료인지 실패인지와 걸린 시간, Task별 상태와 검사·검토 결과,
GitHub까지 진행하는 Job이면 PR과 CI와 병합 준비 여부, 워커가 한도 대기나 재시작으로 멈춘 횟수가 들어
갑니다. 질문에 누가 답했고 누가 완료를 강제했는지(사람, 코디네이터, Astera)도 적고, 검사를 건너뛰었거나
sandbox 밖에서 돌았다면 `주의할 점`에 올립니다. Run이 끝난 시점의 기록이라 그 뒤의 변화는 반영하지
않습니다.

- **PR 댓글**: GitHub까지 진행하는 Job은 같은 요약을 그 Run의 PR에 댓글로 남깁니다. 계정과 토큰은
  빼고, 내 컴퓨터의 경로는 다듬어서 올립니다. 댓글은 한 번만 달고, Run이 다시 끝나면 그 댓글을 고치며,
  사람이 지운 댓글은 다시 달지 않습니다. 설정 › GitHub의 `Run 이 끝나면 PR 에 요약 댓글 남기기`로
  끕니다. 새 Job은 켜진 채로 만들어지고, 이미 있는 Job은 만들 때의 값을 씁니다.
- **Slack**: 예약 실행을 포함한 모든 Run의 요약을 Slack 채널에 올립니다. Host가 Slack을 맡고 있을
  때만 올라갑니다. 설정 › Slack의 `Run 이 끝나면 요약 올리기`로 끕니다. 기본은 켜짐입니다.

이 기능이 생기기 전에 끝난 Run에는 카드가 없습니다.

## 5. 지우기

워크트리를 쓴 Job을 지우면 확인 창에 선택지 셋이 뜹니다. 전부 기본은 꺼짐입니다.

- **프로젝트 폴더에 병합하기**
- **히스토리 목록에서 감추기** — 목록에서만 빼고 기록은 지우지 않습니다
- **워크트리 폴더 삭제**

**병합이 먼저이고, 실패하면 아무것도 지우지 않습니다.** 병합을 골랐는데 실패한 뒤 지우면
워커의 일이 브랜치째 사라집니다.

### 합치지 않고 지워도 일은 사라지지 않습니다

워크트리 폴더를 지울 때, 아직 합쳐지지 않은 커밋이 있는 브랜치는 git이 삭제를 거부합니다.
폴더는 없어져도 그 일은 브랜치 이름으로 되찾을 수 있습니다. 이미 합쳐진 브랜치만 함께
지워집니다.

## 6. 실패하면

실패는 조용하지 않습니다. 전부 Gate로 보이고, Gate에는 사람이 읽을 수 있는 이유가 들어갑니다.

| 상황 | 결과 |
|---|---|
| 프로젝트가 git 저장소가 아님 | Job이 돌지 않습니다. 위의 "먼저" 절을 참고하세요 |
| HEAD가 브랜치를 가리키지 않음 | 같습니다. 브랜치를 체크아웃한 뒤 Gate를 해결하세요 |
| 쓸 수 있는 계정이 없음 | Gate |
| 병합 충돌 | 통합 Task로 넘기거나, 넘길 자리가 없으면 Gate |

### 고른 문제를 한 번 더 고치게 하기

문제 탭에서 Task 의 검사나 검토가 찾은 문제를 골라 **에이전트로 고치기**를 누르면, 그 Task 에 수리를 한 번 더
요청합니다. CLI 로는 `astera tasks repair --task <taskId> [--finding <ref>]` 입니다.

- 받는 Task: 실패한 Task, 수리를 다 써서 막힌 Task(그 질문에 "한 번 더" 로 답한 것과 같습니다), 그리고 완료된 Task
  가운데 Run 이 아직 끝나지 않았고, 그 결과 위에서 시작한 Task 가 줄줄이 따라가도 하나도 없는 것.
- 어느 경우든 마지막 시도의 작업 폴더가 남아 있어야 하고, 다른 Task 가 지금 그 폴더에서 일하고 있으면 안 됩니다.
- 완료된 Task 를 다시 열면, 그 결과를 기다리던 Task 는 이 Task 가 다시 완료될 때까지 대기로 돌아갑니다. 고치는
  중인 결과 위에서 다음 Task 가 시작하지 않게 하기 위해서입니다.
- 그 밖이면 이유를 말하고 받지 않습니다. 앱은 그때 새 Job 초안을 권합니다. 확인 창을 띄운 사이에 상황이 바뀌어
  거절되어도 똑같이 권합니다.
- 한 번에 고른 문제 20개까지 갑니다. 더 고르면 확인 창이 앞의 몇 개만 가는지 말합니다.
- 수리는 마지막 시도의 폴더에서 돌고, 워커는 고른 문제를 맨 먼저 읽습니다. 끝나면 그 Task 의 검사가 다시 돕니다.
  앱이나 Host 가 그 사이 꺼졌다 켜져도, 다시 시작한 수리는 고른 문제를 그대로 들고 갑니다.
- 사람이 요청한 수리는 자동 수리 횟수에 들어가지 않습니다.

**에이전트에게 보내기**로 문제를 세션 입력창에 붙일 때는, 그 문제의 파일을 찾은 폴더에서 일하는 세션만 고를 수
있습니다. Task 의 작업 폴더(worktree)가 남아 있으면 문제는 그 폴더의 파일을 가리키므로, 그 폴더에서 일하는 세션이
받습니다. 서로 다른 작업 폴더의 문제를 한꺼번에 고르면 한 세션에 보낼 수 없다고 말합니다.

### 문제의 상태와 기록

수리를 요청하거나 무시한 문제에는 문제 탭 행에 상태 표시가 붙습니다. 표시를 누르면 그 문제가 언제, 누구 때문에,
어떻게 바뀌었는지가 행 아래에 펼쳐집니다.

- **수리 요청됨**: 사람이 그 문제의 수리를 요청했습니다.
- **확인 대기**: 수리가 잘 끝났고, 그 Task 의 검사나 검토가 다시 돌기를 기다립니다. 수리가 실패로 끝나면 **아직 남음**이
  됩니다.
- **아직 남음**: 다시 돈 검사나 검토가 그 문제를 또 찾았습니다.
- **확인됨**: 다시 돈 검사나 검토가 그 문제를 더 찾지 않았습니다. 문제 탭에서는 사라지고, 기록은 남아 같은 문제가
  다시 나오면 함께 보입니다. 사람이 이 상태로 바꿀 수는 없습니다.
- **무시함**: 사람이 이유를 적고 무시했습니다.

확인됨은 검사가 그 문제를 다시 봤다는 것이 확실할 때만 됩니다. 검사가 돌지 않았거나, 돌 수 없었거나, 센 문제를
다 적지 않았으면 상태를 바꾸지 않습니다. 문제가 보이지 않는다는 것만으로 고쳐졌다고 읽지 않습니다.

문제를 골라 **무시**를 누르면 이유를 물은 뒤 무시합니다. 무시한 문제는 흐리게 남고 개수에서 빠지며, 다음 회차에 같은
문제가 다시 나와도 무시한 채로 있습니다. 판정은 바뀌지 않습니다. 실패한 검사는 실패한 채이고, 막는 검토 이슈는 계속
막고, 자동 수리도 그 문제를 그대로 봅니다. 문제를 지정하지 않은 수리 요청에서는 무시한 문제가 빠집니다. 무시한
문제만 고르면 버튼이 **무시 취소**가 되고, 누르면 무시하기 전 상태로 돌아갑니다. CLI 로는 `astera tasks findings`,
`astera tasks dismiss`, `astera tasks undismiss` 입니다.

## 7. 예약 Job

예약을 켜면 **그 Job 자체는 한 번도 돌지 않습니다.** 정의를 담는 틀(템플릿)이 됩니다.
발화 시각마다 자식 Job 하나(회차)를 만들어 그것을 돌립니다. 회차는 실행 기록입니다.

```
"매일 09:00 리포트"   ← 템플릿. 돌지 않습니다. Task 정의만 들고 있습니다
   ├── 3회차
   ├── 2회차
   └── 1회차
```

Job 하나를 반복해서 돌리면 지난 실행의 Task 상태와 이벤트를 매번 지워야 하고, 그러면 어제 무엇이
실패했는지 볼 수 없습니다. 회차를 따로 두면 기록이 남습니다.

### 만들기와 발화

새 작업 모달에서 `예약 실행`을 켜고 규칙을 고릅니다 — N분마다, 매일, 매주, 매월.

**Task를 다 짜고 `실행`을 눌러야 예약이 시작됩니다.** 보통 Job과 같습니다 — 다만 누르는 순간
도는 것이 아니라, 그때부터 예약이 유효해집니다. 08:59에 눌렀고 규칙이 매일 09:00이면 1분 뒤
첫 회차가 돌고, 09:01에 눌렀으면 다음 날 09:00입니다.

누르기 전까지는 발화하지도, 다음 시각을 잡아 두지도 않습니다. 잡아 두면 Task를 짜는 동안 지나간
시각이 첫 발화가 되어, 버튼을 누르는 순간 이미 밀린 회차가 돕니다.

그 뒤로는 앱이 15초마다 확인해서 시각이 지났으면 회차를 만들고 즉시 돌립니다.

**앱을 켠 직후에는 발화하지 않습니다.** 처음 본 템플릿은 다음 시각만 잡아 둡니다. 그러지 않으면
앱을 켤 때마다 한 회차가 돕니다.

**놓친 발화는 버립니다.** 앱이 꺼져 있던 동안의 시각을 따라잡지 않고 다음 시각부터 셉니다.

### 일시 중지와 다시 실행

사이드바의 템플릿 줄에 `⏸` / `▶` 토글이 있습니다. 상세 창에는 두지 않았습니다 — 그 창의 `실행`
버튼은 **처음 시작하는** 버튼이고, 세우고 다시 돌리는 것은 그것과 다른 일입니다.

**일시 중지하면 지금 도는 워커까지 멈춥니다.** 그 예약에 딸린 회차 전부가 함께 세워지고, 확인 창이
먼저 뜹니다. `worker-retain`으로 붙잡아 둔 세션이 있으면 멈추지 않습니다 — 먼저 놓아 주세요.

**멈춘 회차는 이어지지 않습니다.** 다시 실행하면 **다음 예약 시각에 새 회차**가 돕니다. 중단된
회차의 Task는 멈춘 채로 남습니다.

멈춘 동안 템플릿 줄에는 `다음 …` 대신 `일시 중지됨`이 뜹니다.

### 회차가 도는 방식

회차는 템플릿의 Task를 의존 관계까지 그대로 복사해서 받고, 그 뒤로는 보통 Job과 똑같이 돕니다 —
자기 워크트리가 생기고, 동시 실행 값에 따라 순서대로 또는 나란히 돕니다.

**겹침을 막지 않습니다.** 5분마다 도는데 한 회차가 7분 걸리면 두 회차가 동시에 돕니다. 각자 자기
워크트리에 있으므로 서로를 밟지는 않습니다.

회차에서는 Gate 응답, Task 재시도, 워커 정지가 모두 됩니다. **Task를 추가하거나 고치는 것은
템플릿에서만 됩니다** — 회차에서도 고칠 수 있으면 어느 정의가 진짜인지 알 수 없게 됩니다.

### 회차가 끝나면

**완료된 회차의 워크트리 폴더를 자동으로 지웁니다.** 회차마다 폴더가 쌓이는 것을 막습니다.

폴더는 없어지지만 **그 회차가 한 일은 남습니다.** 아직 합쳐지지 않은 커밋이 있는 브랜치는 git이
삭제를 거부하므로 브랜치가 살아남고, 로그에 그 이름이 남습니다.

**실패한 회차는 폴더를 남깁니다.** 실패는 그 폴더를 열어 볼 이유입니다.

**예약 회차의 결과는 프로젝트에 자동으로 합쳐지지 않습니다.** 폴더가 없어졌으므로 `병합` 버튼도
닿지 않습니다(누르면 합칠 것이 남아 있지 않다고 알려 줍니다). 가져오려면 그 브랜치를 직접
합치세요.

그래서 예약은 **돌리는 것 자체가 목적일 때** 맞습니다 — 테스트를 매일 돌려 결과를 보거나, 리포트를
만드는 일. "매일 고쳐서 프로젝트에 반영해 달라"는 아직 이 기능의 모양이 아닙니다.

### 사이드바

템플릿 줄은 언제나 위쪽에 있습니다. 회차가 쌓일수록 아래로 내려가면 정의를 찾기 어려워집니다.
그 줄에 규칙 요약, 다음 발화 시각, 지금까지 발화한 횟수가 뜹니다. 한 번도 돌지 않았으면 `대기 중`
입니다. 회차는 템플릿 밑에 접혀 있고 펼치면 최신순으로 나옵니다.

**회차 번호는 뒤로 가지 않습니다.** 5회차까지 갔을 때 앞의 두 개를 지워도 다음은 6회차입니다.
번호를 발화 시점에 찍어 두기 때문입니다.

### 지우기

회차 하나만 지우면 그 기록만 사라지고, 보통 Job과 같은 선택지 셋이 뜹니다.

**템플릿을 지우면 회차 전부가 함께 사라집니다.** 도는 워커는 정지시키고 지웁니다. 다만
`worker-retain`으로 붙잡아 둔 세션이 있으면 지우지 않습니다 — 먼저 놓아 주세요.

기록은 30일 뒤 자동으로 정리됩니다.

### 보통 Job과 다른 점

| | 보통 Job | 예약 Job |
|---|---|---|
| 시작 | 사람이 `실행` | 예약 시각 |
| Job 개수 | 하나 | 템플릿 1 + 회차 N |
| 워크트리 | 하나 | 회차마다 하나 |
| 끝난 뒤 폴더 | 남습니다 | 자동으로 지웁니다 (실패는 남김) |
| 프로젝트로 합치기 | `병합` 버튼 | 버튼이 닿지 않습니다 — 브랜치를 직접 합치세요 |
| Task 수정 | 됩니다 | 템플릿에서만 |
| 겹침 | 없습니다 | 허용합니다 |

## 8. GitHub까지 진행

Job을 만들 때 `GitHub 까지 진행`을 켜면, Astera가 각 Run의 일을 GitHub의 pull request로 가져가 CI를
통과하고 검토를 마칠 때까지 끌고 갑니다. **병합은 하지 않습니다.** Astera의 일은 병합 준비 완료까지이고,
병합은 사람이 GitHub에서 합니다.

### 켜기

- 새 작업 모달과 `소스에서` 창의 `GitHub 까지 진행`입니다. 기본은 꺼짐입니다. 켜면 Host가 그 폴더를 먼저
  확인합니다: origin이 GitHub 저장소인지, `gh` 로그인이 되어 있는지, 내 권한이 WRITE·MAINTAIN·ADMIN인지.
  안 되면 이유를 보여 주고 `만들기`(소스 창에서는 `작업 만들기`)를 막습니다. 켜면 `통과할 때까지 자동
  수정`도 함께 켜집니다.
- CLI는 `astera jobs create --github-lifecycle`, MCP는 `create_job`의 `githubLifecycle`입니다. MCP는 설정
  › CLI의 MCP 접근이 `읽기와 제어`이고 `MCP 클라이언트가 GitHub 에서 작업하게 하기`가 켜져 있어야 합니다.
- 기다릴 검사를 이름으로 고르는 것(`--github-checks build,test`)은 CLI와 MCP에서만 합니다. 고른 검사는
  저장소가 필수로 정한 검사와 함께 판정합니다. 고르지 않으면 브랜치 규칙의 필수 검사가, 필수 검사가
  없으면 보고된 검사 전부가 판정합니다.

### 설정 › GitHub의 기본값

새 Job이 만들어질 때 가져가는 값입니다: 코드 밖의 이유(러너 장애, 네트워크)로 실패한 CI를 다시 돌릴지,
최대 몇 번(1~10), CI를 몇 분(10~1440) 기다릴지. 만든 뒤에 바꿔도 이미 있는 Job은 만들 때의 값을 씁니다.
`Run 이 끝나면 PR 에 요약 댓글 남기기`도 같은 자리에 있고, 같은 방식으로 새 Job에만 적용됩니다(4절의
`결과 보고`).

### 도는 방식

보통 Task가 모두 끝나면 Astera가 `GitHub 전달` Task를 하나 더합니다. 워커가 없는 Task입니다.

1. Task들의 결과를 Run의 브랜치에 모은 뒤 로컬 검사를 다시 돌립니다.
2. 브랜치를 GitHub에 푸시하고, 그 브랜치에 열린 PR이 없으면 초안 PR을 엽니다. 같은 저장소의 이슈에서
   만든 Job이면 PR 본문에 `Refs #N`이 들어갑니다.
3. 푸시한 head의 CI를 기다립니다.
4. 코드 때문에 실패하면 수리 워커가 고치고 1부터 다시 합니다(횟수는 자동 수정의 예산을 씁니다). 코드 밖의
   이유면 설정한 만큼 CI를 다시 돌립니다.
5. CI가 통과하면 마지막으로 구현한 provider와 다른 provider의 리뷰어가 PR 전체를 검토합니다. 설정에서 외부 검토자를 골랐다면 그 에이전트가 검토합니다(3절).
6. 검토가 통과하면 **병합 준비 완료**입니다. 그 뒤에 head가 바뀌거나, base가 바뀌거나, 판정한 검사가
   실패하거나 그 목록이 바뀌거나, PR이 닫히거나 병합되면 거둬들이고 이유를 남깁니다.

### 앱에서 보이는 것

- Jobs 카드의 칩: 병합 준비, CI 대기, CI 수리 중.
- Run 상세의 GitHub 블록: PR(초안 표시), head, 검사 목록, 지금 상태와 수리 횟수, 실패한 검사와 이유,
  병합 준비와 GitHub 자신의 상태(초안·차단·충돌), Astera가 푸시하지 않은 커밋, 로컬 검사를 지정한
  Task가 없을 때의 경고(모든 수리가 로컬 확인 없이 GitHub CI로 갑니다).
- 타임라인: PR 열림·연결, 푸시, CI 시작·실패·다시 돌림·통과, 병합 준비, 병합 준비 아님, 소스 이슈 바뀜.

### 질문

Astera가 혼자 정할 수 없는 일은 질문으로 묻고, 답할 때까지 그 회차의 CI 대기를 그대로 둡니다. CI가
나타나지 않음, 기다리는 시간을 넘김, Astera가 푸시하지 않은 커밋, 그 브랜치에 열린 PR이 여럿, PR이 닫히거나
병합됨, 코드 밖의 실패, GitHub으로 가져가지 못함이 그렇습니다. 답(`다시 기다리기`, `CI 없이 진행`, `받아서
이어 가기`, `다시 시도`, `다시 돌리기`, `PR #N 로 묶기`, `Task 를 실패로 처리`)은 앱에서 누르면 Host가
처리합니다. Host가 꺼져 있으면 그렇다고 알려 줍니다.

### 다시 가져가기

`GitHub 전달` Task가 끝난 뒤(통과든 실패든) 다시 GitHub으로 가져가려면 `astera runs reconverge --id
<runId>`(MCP `reconverge_run`)를 씁니다. 묶인 PR이 병합되거나 닫혀 있으면, 또는 Run의 워크트리가 없으면
거절합니다.

### 원격 Runtime

전체 제어로 페어링한 기기는 GitHub까지 진행하는 Run의 GitHub 상태를 읽고 `runs reconverge`를 쓸 수
있습니다(읽기 전용 페어링은 읽기만). 원격에서 만든 Job은 그 Runtime의 설정 › GitHub 기본값을 쓰고,
푸시·PR·CI 다시 돌림은 그 Runtime의 Host가 그 머신의 `gh` 로그인으로 합니다. 기기에서 GitHub에 직접 쓰는
명령은 없고, 원격에서는 이슈가 아니라 목표로 Job을 만듭니다.

## 부록: 워크트리는 어디에 생기나

| | |
|---|---|
| 폴더 | `~/astera-worktrees/<저장소 이름>/<작업명>` |
| 브랜치 | `<git 사용자명>/<작업명>` |
| 갈라지는 자리 | 프로젝트 폴더의 현재 브랜치 |

작업명은 Job의 목표(Task라면 제목)에서 만들고, 길어도 40자에서 자릅니다. 되도록 단어 중간이
아니라 그 앞의 `-` 자리에서 자르므로, 한 문단짜리 목표도 폴더와 브랜치 이름이 길어져 실패하지
않습니다. git이 받지 않는 `.lock` 으로 끝나는 이름은 `-lock` 으로 바꿉니다.
같은 이름이 이미 있으면 뒤에 숫자가 붙습니다. 워크트리 목록은 탐색기의 워크트리 패널에서 볼 수
있고, 폴더가 사라진 항목은 목록을 열 때 저절로 정리됩니다.
