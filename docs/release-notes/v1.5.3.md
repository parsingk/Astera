## New features

* **A report when a Run ends.** When a Run finishes, the Host writes a summary of it and keeps it with the Run. It is
  the card at the top of the Run's details, and **Copy** takes it as Markdown. It says whether the Run completed or
  failed and how long it took, each Task's state with its check and review results, the pull request, CI and merge
  readiness of a Job that goes to GitHub, how often workers stopped for a limit wait or a restart, and who answered
  questions or forced a completion (a person, the coordinator or Astera). A check that was skipped or ran outside the
  sandbox is listed under **Caveats**. Runs that ended before this version have no card.
* **The report on the pull request and in Slack.** A Job that goes to GitHub comments the same summary on its Run's
  pull request, with accounts and tokens left out and paths on your computer trimmed. It comments once, edits that
  comment when the Run ends again, and does not post again a comment someone deleted. New Jobs do this by default
  (**Settings › GitHub**, **Comment a summary on the pull request when a Run ends**). Jobs made before this version keep
  the setting they were made with, so they do not comment. While the Host runs Slack, every Run's summary, scheduled
  Runs included, is posted to the Slack channel. This is on by default, so after the update a channel set up for Astera
  gets a post at the end of each Run. Turn it off with **Settings › Slack**, **Post a summary when a Run ends**.
* **External reviewers.** A Task that asks for a review (`--review`) is reviewed by the other provider's model. Now
  another agent can review it instead: Gemini CLI, Copilot CLI, OpenCode or any agent that speaks ACP. Add one in
  **Settings › Agents › Reviewer** with **Add reviewer** and choose it. **Test** starts the agent briefly and says
  whether it connected, needs a sign-in, was not found or did not answer in time. The agent must already be installed
  and signed in on that computer. Astera asks it only to read: anything else it asks permission for is refused, and the
  review stops if it changes a file. A review it cannot finish never falls back to the other provider. The Task stops
  and asks you, and work that ran in a sandbox is not handed to it. The Host runs these reviews while Astera is closed
  too. The reviewer's name shows in the Run's details and its report, and what the agent said is kept for 14 days in
  the `review-logs` folder of the profile. With **Automatic (the other provider)** chosen nothing changes, except that
  the Run report names the reviewer.
* **Claude Code's shell runs in a sandbox on Windows.** Claude Code has no sandbox of its own on Windows, so a
  sandboxed agent profile's Claude session there only kept its file tools out of the login folders and ran its shell
  unrestricted. Its shell commands now run in Codex's Windows sandbox, under the same rules a sandboxed Codex session
  gets, when Git Bash is found and a Codex account is registered with its Windows sandbox set up. **Settings › Agent
  profiles** shows the Codex account the shell borrows, with **Set up** when that account's sandbox is not set up yet.
  In such a session the PowerShell tool is off, and `.claude` in the work folder and an existing `.mcp.json` are
  read-only to the shell, so a command cannot plant something Claude Code would run outside the sandbox. They stay
  read-only to the shell of every later sandboxed session in that folder, Codex's included; the file tools can still
  write them. Each command takes one to two seconds longer. Without that route the session starts as before and says
  why. A Claude worker's checks and a Claude reviewer on Windows run in Codex's sandbox the same way.
* **Kubernetes manifests.** Astera recognises Kubernetes manifests and Kustomize files in a project and shows them with
  the Kubernetes icon. A manifest open in the editor gets a toolbar: the cluster (a kubeconfig context, remembered per
  folder) and namespace it goes to, a chip that says whether the file is the same as the cluster, differs from it or is
  not there yet, and **Compare with cluster**, **Apply to cluster…**, **Reload from cluster** and **Delete from
  cluster…**. The explorer's right-click menu has the same actions in a **Kubernetes** submenu, for a file, several
  files, a folder or a Kustomize overlay. A Kustomize patch is applied through its overlay, and **Show what Kustomize
  builds** shows the merged result beside it. Every operation is logged in a **Kubernetes** tab, where it can be run
  again, stopped or copied as a command. **Settings › Kubernetes** sets the kubectl path and adds kubeconfig files.
  kubectl must be installed. Helm charts are not supported yet.
* **Every change to a cluster is confirmed first.** Applying or deleting opens a confirmation that runs a server dry
  run and shows each resource side by side, the cluster now against the result, with Secret values hidden, along with
  the kubectl commands it will run, which you can copy. Only what that confirmation showed is run: if the files changed
  after it, Astera compares again and asks once more. Choosing a cluster never changes your kubeconfig. Only **Set … as
  the kubeconfig current context** in the cluster picker does.
* **A new Namespace or CRD is applied first.** When an apply's dry run fails because a Namespace or
  CustomResourceDefinition in the same files is not in the cluster yet, the confirmation lists them under **Apply these
  first** with an **Apply first** button. That applies only those, after a confirmation of its own, waits for a CRD to
  be ready, and then opens the original confirmation again.

## Fixes

* **Sandboxed sessions can no longer read the agents' login files.** A sandboxed session's shell could open Claude
  Code's `.credentials.json` and Codex's `auth.json`, the files the agents keep their logins in (seen on Windows). Every
  sandbox Astera starts now denies them, in the default folders and in every account's folder.
* **A Codex sandbox on a busy Windows PC is checked to the end.** Starting a sandboxed Codex session on Windows could
  fail with "Codex could not be asked about this account's Windows sandbox" when `codex doctor` took longer than 30
  seconds, which it does on a busy Codex home (25 to 43 seconds measured). Astera now waits up to two minutes.
* **Terminal hyperlinks open.** Clicking a link a program prints as a terminal hyperlink (Claude Code prints artifact
  addresses this way) asked "Do you want to navigate to …?", did not open the link even after OK, and stopped typing
  from working for a while. These links now open the way a printed address does.
